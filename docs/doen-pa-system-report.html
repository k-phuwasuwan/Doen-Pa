1. ภาพรวมโปรเจค

Doen Pa (เดิ่นป่า) คือ Digital Hiking Passport ส่วนตัวสำหรับนักเดินป่าชาวไทย แนวคิดหลักคือ “บันทึกการเดินทาง ไม่ใช่วางแผนการเดินทาง” ผู้ใช้ค้นหาสถานที่ → “ประทับตรา” การเยือนด้วยการสร้าง travel record (วันที่ รูป ข้อความ คะแนนส่วนตัว) → ดูความทรงจำใน Passport, หน้ารายละเอียดสถานที่, แผนที่, สถิติ และโปรไฟล์

156อุทยานแห่งชาติใน catalog
123แห่งมีรูปถ่ายลิขสิทธิ์เปิด
7หน้าหลัก (ค้นหา แผนที่ พาสปอร์ต สถิติ โปรไฟล์ …)
63unit/DB test (+ e2e Playwright 14 สเปค)

สิ่งที่อยู่ในขอบเขต (MVP)

  • ค้นหา/กรองสถานที่ (ประเภท ภูเขา น้ำตก ถ้ำ หมู่เกาะ · เคยไปแล้ว/ยังไม่เคย)
  • หน้ารายละเอียดสถานที่ และการประทับตราสร้างบันทึกการเดินทาง (สูงสุด 5 รูปต่อบันทึก)
  • Passport (รายการบันทึกทั้งหมด) · แผนที่เฉพาะที่เคยไป · สถิติรายจังหวัด/ภาค/ประเภท/อุทยาน · โปรไฟล์
  • บัญชีผู้ใช้ด้วยอีเมล/รหัสผ่าน (สมัคร ยืนยันอีเมล เข้าสู่ระบบ กู้รหัสผ่าน ออกจากระบบ)

สิ่งที่อยู่นอกขอบเขตจนกว่าจะอนุมัติ

ระบบ badge, social, โปรไฟล์/รีวิว/คะแนนสาธารณะ, จอง/ชำระเงิน, วางแผนเส้นทาง, GPS สด, พยากรณ์อากาศ, ระบบแนะนำ, activity feed, ข้อความ — คะแนนดาวของผู้ใช้เป็นข้อมูลส่วนตัวเท่านั้น ไม่ถูกรวมเป็นคะแนนสาธารณะ

สถานะปัจจุบัน

  • รันจริงบน Vercel ที่ https://doen-pa.vercel.app ใช้ Supabase (Auth, Postgres, Storage) เป็น backend ทั้งหมด
  • ดีไซน์ปัจจุบันคือ “Contour & Stamp” (เขียวป่า พื้นหลังเส้นชั้นความสูง ตราประทับหมึก กระจก Liquid Glass)
  • เลื่อนไว้: Google login, หน้า badge, นโยบายรูปสถานที่ถาวรระยะยาว

3. สถาปัตยกรรมระบบ (Architecture)

ระบบเป็นแอป Next.js ตัวเดียวบน Vercel ที่คุยกับ Supabase เป็นแหล่งข้อมูลเดียว ไคลเอนต์เรียก Supabase ได้โดยตรงสำหรับการเขียนที่ต้องมีธุรกรรมและการอัปโหลดรูป ส่วนการอ่านข้อมูลส่วนตัวผ่านเซิร์ฟเวอร์ของเราเพื่อให้ตรวจตัวตนก่อนทุกครั้ง

หลักการออกแบบสำคัญ

  • Server Components เป็นค่าเริ่มต้น ใช้ Client Components เฉพาะเรื่องที่ต้องใช้ API เบราว์เซอร์ (Leaflet ฟอร์ม ตัวกรอง state บัญชี)
  • ความจริงอยู่ที่ฐานข้อมูล ไม่มี catalog สำรองในแอป ถ้าโหลด catalog ไม่ได้ จะแสดงหน้า “โหลดข้อมูลไม่สำเร็จ” แทนที่จะแสดงสถิติว่างเปล่าที่ผิดความจริง
  • ตรวจสิทธิ์สองชั้น เซิร์ฟเวอร์ตรวจตัวตนก่อน render ข้อมูลส่วนตัว และ RLS ในฐานข้อมูลบังคับสิทธิ์อีกชั้นแม้โค้ดผิดพลาด
  • เขียนข้อมูลแบบ atomic บันทึกการเดินทางและรูปที่เกี่ยวข้องถูกยืนยันเข้าฐานข้อมูลในฟังก์ชัน RPC เดียว

4. การเชื่อมต่อและการรับส่งข้อมูล

ตารางนี้แสดงว่าใครคุยกับใคร ส่งอะไร ด้วยการยืนยันตัวตนแบบไหน และแคชอย่างไร (ไคลเอนต์ ↔ เซิร์ฟเวอร์ ↔ อินเทอร์เน็ต) การสื่อสารทั้งหมดเป็น HTTPS

4.1 ไคลเอนต์ ↔ เซิร์ฟเวอร์ Next.js (Vercel)

ช่องทางเมธอดข้อมูลที่ส่ง → ได้รับยืนยันตัวตน/แคช
หน้าเว็บ /search, /places/[id], /passport …GETส่ง cookie session + query (q, type, visited, from, photo) → ได้ HTML/RSC ที่ render แล้ว (catalog 156 แห่งฝังมากับหน้า Search)cookie Supabase (SameSite=Lax) · ข้อมูลส่วนตัวไม่แคชร่วม
/api/accountGETส่ง cookie → ได้ JSON: โปรไฟล์ ข้อมูลบันทึกการเดินทาง และ metadata รูป ของผู้ใช้คนนั้น (ดึงซ้ำเมื่อโฟกัสหน้าต่าง/แท็บอื่นเปลี่ยนข้อมูล)getUser() ยืนยันจริง · no-store
/api/photos/[id]?owner=&w=GETส่ง id รูป + owner + ความกว้าง (256/640/1280) → ได้ไฟล์รูป (WebP ย่อแล้ว หรือต้นฉบับ)getClaims() + RLS · private, max-age=1 ปี, immutable (เบราว์เซอร์เดียวของเจ้าของ)
/auth/login, signup, resend, forgot-password, logout, complete-profile-setup, delete-account, …POST (JSON)ส่งอีเมล/รหัสผ่าน หรือคำสั่ง → ได้ JSON ผลลัพธ์ + next ปลายทาง; ตั้ง/ล้าง cookie sessionรับเฉพาะคำขอ same-origin แบบ JSON · private, no-store · ส่ง Clear-Site-Data: "cache" เมื่อ login/logout/ลบบัญชี
/auth/confirmGETลิงก์ในอีเมล: token_hash + type (email/recovery) → แลกเป็น session แล้ว redirect (สมัครใหม่ → ตั้งโปรไฟล์, กู้รหัส → /reset-password)token ใช้ได้ครั้งเดียว; เปิดต่างอุปกรณ์ได้
/auth/callbackGETรองรับลิงก์แบบ PKCE (code) — ต้องเปิดในเบราว์เซอร์เดียวกับที่เริ่ม จึงไม่ใช้กับอีเมลปัจจุบันต้องมี code verifier cookie
ไฟล์ static (/images/parks/{640,1280}/*.webp, ฟอนต์, thailand.json)GETรูปอุทยาน ฟอนต์ และเส้นแบ่งจังหวัด — ไม่ผ่าน proxyแคชด้วย CDN ของ Vercel

4.2 ไคลเอนต์ ↔ Supabase โดยตรง (เบราว์เซอร์ → อินเทอร์เน็ต)

การทำงานรายละเอียด
อัปโหลดรูปเข้า Storageเบราว์เซอร์ลบ EXIF/XMP/GPS ออกก่อน (strip-metadata.ts) แล้ว upload ไปที่ travel-photos/<uid>/record-photos/<id>.ext หรือ profile-photos ด้วย JWT ของผู้ใช้ — policy บังคับให้เขียนได้เฉพาะโฟลเดอร์ของตัวเอง
RPC save_travel_recordส่ง JSON ของบันทึก + รายการรูปที่อัปโหลดแล้ว ฟังก์ชันตรวจว่าไฟล์อยู่ใน Storage ขนาดและชนิดตรงกันจริง ก่อน insert ทั้งหมดในธุรกรรมเดียว; ID ที่ส่งซ้ำ (retry) ไม่สร้างซ้ำ
RPC save_account_profileบันทึกชื่อ/username/bio พร้อม metadata ของอวตาร์/ปก แบบ atomic แล้วคืนรายการไฟล์เก่าที่ต้องลบ
ลบไฟล์เก่า (cleanup)ลบไฟล์ใน Storage หลังข้อมูลใน DB เปลี่ยนแล้วเท่านั้น (policy ไม่ให้ลบไฟล์ที่ยังถูกอ้างอิง)

4.3 เซิร์ฟเวอร์ ↔ Supabase และบริการอื่น

การเชื่อมต่อรายละเอียด
อ่าน catalog placesREST ด้วย publishable key (สิทธิ์ SELECT อย่างเดียว) no-store แบ่งหน้า 500 แถว timeout 10 วินาที ตรวจรูปแบบข้อมูลก่อนใช้ แคชหนึ่ง snapshot ต่อหนึ่ง request ด้วย React cache
อ่านข้อมูลบัญชีด้วย SSR client ที่ถือ session ผู้ใช้ (ผ่าน RLS) อ่านเป็นหน้า ๆ ตามจำนวนจริง เพื่อไม่ให้เพดานแถวของโปรเจคตัดข้อมูลผู้ใช้
Supabase Auth → Gmail SMTPSupabase ส่งอีเมลยืนยัน/กู้รหัสผ่านผ่าน SMTP ที่ตั้งไว้ (เทมเพลตภาษาไทยแก้ที่ Supabase dashboard ไม่ได้ deploy ไปกับ Vercel)

4.4 เบราว์เซอร์ ↔ บริการภายนอก

บริการรายละเอียด
Stadia MapsLeaflet ขอกระเบื้อง PNG จาก tiles.stadiamaps.com ส่ง Referer ของเว็บให้ตรวจโดเมน (แคชได้ 24 ชั่วโมง)
นโยบาย CSPจำกัดแหล่งที่เบราว์เซอร์ติดต่อได้: img-src 'self' data: blob: tiles.stadiamaps.com, connect-src 'self' https://*.supabase.co, ห้าม frame, ห้าม object
สรุปเส้นทางที่ “ไม่” ผ่านเซิร์ฟเวอร์เรา: ไบต์ของรูปส่วนตัวตอนอัปโหลด (เบราว์เซอร์ → Supabase Storage) และการเรียก RPC ตอนบันทึก ส่วนตอน “ดู” รูป ไบต์ผ่าน /api/photos เสมอ เพื่อให้เซิร์ฟเวอร์ตรวจสิทธิ์ก่อนและควบคุมการแคช

6. โมเดลข้อมูลและความสัมพันธ์ของข้อมูล

จุดออกแบบที่ควรรู้

  • travel_records.place_id ไม่มี foreign key ไป places โดยตั้งใจ เพื่อให้บันทึกเก่าที่อ้าง ID ซึ่งเปลี่ยนชื่อหรือถูกเลิกใช้ ยังอ่านได้ ไม่ทำให้ catalog ใหม่ทำลายข้อมูลผู้ใช้ มีตารางนามแฝงใน place-identities.ts และข้อมูลสถานที่ย้อนหลังใน archived-places.ts
  • ID ของระเบียนผู้ใช้เป็นข้อความที่ผูกกับบัญชี ((user_id, id) เป็น primary key) ส่ง ID ซ้ำหมายถึง retry จึงไม่สร้างบันทึกซ้ำ
  • รูปต่อบันทึกจำกัด 5 รูป บังคับที่ฐานข้อมูล (position 0–4 และ unique index) ส่วนสถานที่หนึ่งแห่งแสดงรูปรวมจากหลายบันทึกได้ไม่จำกัด
  • รูปอุทยาน (catalog) ไม่อยู่ใน Storage เก็บเป็นไฟล์ static ใน public/images/parks/ โดย DB เก็บเฉพาะชื่อไฟล์และเครดิต
  • สถิติไม่ได้เก็บในฐานข้อมูล คำนวณทุกครั้งจากบันทึกของผู้ใช้ + catalog (นับสถานที่/จังหวัด/อุทยานที่ไม่ซ้ำ)
  • ชนิด Place.type มี 4 ค่า (mountain, waterfall, cave, island) ส่วนการนับ “อุทยานแห่งชาติ” ใช้ฟิลด์ is_national_park แยกต่างหาก ไม่ขึ้นกับประเภทที่แสดง

7. Data Flow

7.1 การอ่านข้อมูล (Read path)

7.2 การเขียนข้อมูล (Write path) — บันทึกการเดินทาง

  1. ผู้ใช้เลือกรูป (JPG/PNG/WebP ≤5 MB, ≤5 รูป) → เบราว์เซอร์ ลบ EXIF/GPS และแสดงตัวอย่าง
  2. เมื่อกดบันทึก account store ยืนยันตัวตนปัจจุบัน แล้วอัปโหลดรูปเข้า travel-photos/<uid>/… โดยตรง
  3. เรียก RPC save_travel_record(record, photos) — ฐานข้อมูลตรวจว่าไฟล์อยู่จริง ขนาด/ชนิดตรง แล้ว insert บันทึก + แถวรูปในธุรกรรมเดียว (ID เดิม = no-op)
  4. สำเร็จ: ส่งสัญญาณข้ามแท็บ (localStorage) → รีเฟรช snapshot → ไปหน้า Passport
  5. ล้มเหลว: ฟอร์มยังเก็บร่างไว้; ระบบพยายามลบไฟล์ที่อัปโหลดไปแล้วแต่ไม่ได้ผูก (ถ้าลบไม่ได้อาจเหลือไฟล์ค้างส่วนตัว ซึ่งต้องล้างภายหลัง)

7.3 การไหลของข้อมูล catalog (ก่อนถึงผู้ใช้)

CSV (data/national-parks-156.csv)        ← แก้ที่นี่ที่เดียว (รวมคอลัมน์รูป/เครดิต)
   │  pnpm import:places  (Python: ตรวจ → สร้าง SQL)
   ▼
supabase/seed.sql                          ← สร้างอัตโนมัติ ห้ามแก้มือ
   │  pnpm db:seed:places  (supabase db query --linked)
   ▼
public.places (Postgres)  ──REST/SELECT──▶  Server Component  ──▶  HTML ที่ผู้ใช้เห็น
public/images/parks/*.webp ──────────── (ไฟล์ static ผ่าน CDN)  ──▶  การ์ด/หน้ารายละเอียด

8. Workflow

8.1 ขั้นตอนพัฒนาและส่งมอบ

  1. แก้โค้ดในเครื่อง (pnpm dev; ถ้ามี dev server ของผู้ใช้อยู่แล้วให้ใช้ตัวเดิม) — dev server ใช้ฐานข้อมูล Supabase ชุดเดียวกับ production
  2. ตรวจ: pnpm exec tsc --noEmit, pnpm lint, git diff --check, pnpm test (ต้อง Node 22+), pnpm build เมื่อจำเป็น
  3. ตรวจหน้าจริงบนเดสก์ท็อปและมือถือเมื่อแก้ UI (อ่านโค้ดหรือ lint อย่างเดียวไม่นับเป็นการตรวจภาพ)
  4. commit แยกตามประเภท feat: fix: style: copy: docs: และอัปเดต AGENTS.md เมื่อพฤติกรรมหรือการไหลของข้อมูลเปลี่ยน
  5. git push → GitHub Actions CI → Vercel deploy จาก main

9. สถานการณ์ใช้งาน (Scenarios)

สถานการณ์ A: ผู้ใช้ใหม่สมัครและตั้งโปรไฟล์

กรณีพิเศษ: (1) สมัครด้วยอีเมลที่มีบัญชีแล้ว Supabase ตอบสำเร็จแต่ ไม่ส่งอีเมล (กันการเดาอีเมล) ผู้ใช้ควรไปหน้าเข้าสู่ระบบ (2) กดส่งซ้ำเร็วกว่า 60 วินาที หรือเกินโควต้าอีเมลต่อชั่วโมง จะได้ข้อความ “ทำรายการบ่อยเกินไป” (3) อีเมลองค์กร/มหาวิทยาลัยอาจกัก/ทิ้งอีเมลเงียบ ๆ (ส่งออกแล้วแต่ไม่ถึง) (4) ปุ่มส่งซ้ำมีตัวนับถอยหลัง 60 วินาที

สถานการณ์ B: ค้นหาอุทยานแล้วประทับตรา

สถานการณ์ C: ดูรูปและแผนที่ที่เคยไป

  • หน้ารายละเอียดจาก Search: ถ้ายังไม่มีรูปของตัวเอง เห็นรูปอุทยานพร้อมเครดิต (ข้อความธรรมดา); เมื่อมีรูปของตัวเอง รูปของผู้ใช้จะแทนที่ (รูปส่วนตัวผ่าน /api/photos)
  • หน้ารายละเอียดจาก Passport/Profile: โหมดอ่านอย่างเดียว ไม่มีปุ่ม Stamp การ์ดข้อมูลกว้างเต็มคอลัมน์
  • แผนที่: แสดงหมุดเฉพาะสถานที่ที่เคยไปและมีพิกัด; เลือกหมุดแล้วขึ้นการ์ดข้อมูล (ไม่นำทางไปไหน) กระเบื้องมาจาก Stadia โดยตรง

สถานการณ์ D: ลืมรหัสผ่าน

กรอกอีเมลที่ /forgot-password → Supabase ส่งลิงก์ (type=recovery) → /auth/confirm แลก session แล้วพาไป /reset-password เสมอ → ตั้งรหัสใหม่ → ระบบออกจากระบบและพาไปหน้า Login ให้เข้าด้วยรหัสใหม่ (บัญชีที่ยังไม่ยืนยันอีเมลไม่สามารถกู้รหัสได้)

สถานการณ์ E: ผู้ใช้ออกจากระบบ/ลบบัญชี

ออกจากระบบ: ยกเลิก session ปัจจุบัน (scope: local) ล้าง cookie และแคชรูป แจ้งแท็บอื่น (ไม่ออกจากอุปกรณ์อื่น) · ลบบัญชี: endpoint /auth/delete-account ตรวจรหัสผ่านซ้ำ → ลบแถวรูปและไฟล์ใน Storage → delete_my_account() ลบผู้ใช้ (ข้อมูลที่เกี่ยวข้องหายตาม cascade) ปัจจุบันยังไม่มีปุ่มใน UI ที่เรียก endpoint นี้ (ถูกเอาออกตามคำขอ)

10. ความปลอดภัยและความเป็นส่วนตัว

ด้านมาตรการในระบบ
การยืนยันตัวตนSupabase Auth; proxy รีเฟรชด้วย getClaims (ตรวจ JWT ในเครื่อง) ส่วนก่อน render ข้อมูลส่วนตัวใช้ getUser ยืนยันกับเซิร์ฟเวอร์ Auth; cookie SameSite=Lax
การควบคุมสิทธิ์RLS แบบ “เจ้าของเท่านั้น” ทุกตารางส่วนตัวและ bucket ส่วนตัว; catalog ให้ SELECT อย่างเดียวแก่ anon/authenticated ไม่มีสิทธิ์เขียน/ลบ/truncate; การนำเข้าใช้สิทธิ์ผู้ดูแลนอกโค้ดไคลเอนต์
ข้อมูลใน requestรับเฉพาะคำขอ JSON same-origin ที่ /auth/*; รายการปลายทาง redirect (next) ผ่านรายการที่อนุญาตเท่านั้น (กัน open redirect)
ความเป็นส่วนตัวของรูปลบ EXIF/XMP/GPS ในเบราว์เซอร์ก่อนอัปโหลด; รูปส่วนตัวไม่เป็นสาธารณะ ส่งผ่านเซิร์ฟเวอร์ที่ตรวจสิทธิ์; แคชเฉพาะเบราว์เซอร์เจ้าของและล้างด้วย Clear-Site-Data เมื่อ login/logout; ไม่ใช้ตัวปรับรูปของ Next (ไม่ให้ไบต์ส่วนตัวเข้าแคชร่วม)
Header ความปลอดภัยCSP จำกัดแหล่งที่มา, X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy (ปิดกล้อง ไมค์ ตำแหน่ง การชำระเงิน)
ความลับApp Password ของ Gmail อยู่ใน Supabase เท่านั้น; คีย์ผู้ดูแลไม่อยู่ใน git/แอป; CI สแกนความลับ
ห่วงโซ่อุปทานCI ตรวจช่องโหว่ dependency ระดับ high ขึ้นไป (production)
ข้อจำกัดที่เอกสารของโปรเจคยอมรับไว้: ไม่มี rate limit ฝั่งแอปสำหรับ login (พึ่ง Supabase) · CSP ยังต้องใช้ 'unsafe-inline' สำหรับสคริปต์ (ข้อมูล hydration ของ Next) · เมื่อตรวจ CSP แล้ว flow ที่ล็อกอิน (อัปโหลด แก้โปรไฟล์) ยังไม่ได้ตรวจใต้ CSP ควรรัน production journey หลัง deploy

11. สิ่งที่ควรรู้ ข้อจำกัด และความเสี่ยง

11.1 เรื่องที่ทำให้ทำงานผิดพลาดได้ง่าย

  • Next.js 16 ต่างจากที่เคยรู้จัก อ่านคู่มือใน node_modules/next/dist/docs/ ก่อนเขียนโค้ด (ใช้ proxy.ts, build ด้วย Webpack)
  • Node 22+ สำหรับเทสต์ ถ้าใช้ Node 20 ที่เป็นค่าเริ่มต้นบางเครื่อง เทสต์ 5 ข้อล้มด้วย “native WebSocket not found” (ไม่ใช่บั๊กโค้ด) CI เองยังตั้ง Node 20 และมีคำเตือน deprecated
  • dev server ใช้ฐานข้อมูลจริง .env.local ชี้ไป Supabase production ไม่มีฐานข้อมูล staging ดังนั้นการทดสอบฝั่งเขียนในเครื่องเขียนข้อมูลจริง (ใช้บัญชี QA ที่แยกไว้)
  • ลำดับ deploy migration ก่อน แล้วค่อยโค้ดที่อ่านคอลัมน์ใหม่ (บทที่ 8.3)
  • เทมเพลตอีเมลต้องวางเองใน dashboard การ push โค้ดไม่เปลี่ยนค่าบน Supabase
  • ห้ามนำข้อมูลตัวอย่างกลับมา ไม่ใส่บันทึกหรือรูปตัวอย่างของผู้ใช้; ห้ามใช้ URL รูป Stitch (lh3.googleusercontent.com/aida-public/…) เป็นแหล่งรูปจริง
  • alt text ของรูป กรอกได้ในฟอร์มแต่ไม่ถูกบันทึก (ต้องตัดสินใจเรื่องโมเดลข้อมูลก่อนแก้)

11.2 บริการภายนอกและข้อจำกัดของแผนที่ใช้อยู่

เรื่องสถานะ/ความเสี่ยง
Stadia Mapsช่วงทดลอง Professional 14 วันจะหมดราว 5 พ.ย. 2569 แล้วย้ายไปแผน Free (200,000 เครดิต/เดือน, ห้ามใช้เชิงพาณิชย์) โปรเจคส่วนตัวไม่มีรายได้จึงใช้ได้ แต่ถ้าเกินโควต้าแผนที่อาจโหลดไม่ได้ และถ้าแอปกลายเป็นเชิงพาณิชย์ต้องเปลี่ยนแผนหรือผู้ให้บริการ ควรเปิดหน้าแผนที่บนเว็บจริงหลังวันที่หมดทดลองเพื่อยืนยัน
การส่งอีเมลใช้ Gmail SMTP ของบัญชีผู้ส่งธรรมดา: โอกาสเข้าสแปม/ถูกกรอง (โดยเฉพาะอีเมลสถาบัน เช่น @go.buu.ac.th) ค่า rate limit อีเมล 30 ฉบับ/ชม. ทั้งโปรเจค และเว้น 60 วินาทีต่อผู้ใช้ (ตามที่ผู้ดูแลแจ้ง) และข้อจำกัดอีเมล Gmail ต่อวัน — ทางแก้ระยะยาวคือใช้โดเมนของตัวเองกับผู้ให้บริการอีเมลธุรกรรม พร้อม SPF/DKIM/DMARC
รูปอุทยานจาก Commonsแสดงเครดิตเป็นข้อความธรรมดา (ผู้ถ่าย · สัญญา) ซึ่งครบข้อบังคับหลักของ CC BY/BY-SA แต่ CC BY 4.0 ยังขอลิงก์ไปยังสัญญา “เมื่อทำได้สมควร” ลิงก์ต้นทางและสัญญายังเก็บใน DB พร้อมทำหน้ารวมเครดิตได้ · 33 อุทยานยังไม่มีรูป (แสดงกรอบ topo)
แผน Supabase Freeควรตรวจนโยบายสำรองข้อมูลและโควต้า (ฐานข้อมูล/Storage/แบนด์วิธ) ของแผนที่ใช้อยู่ ว่ารองรับการเติบโตและการกู้คืนที่ต้องการหรือไม่ (รายงานนี้ไม่ได้ตรวจค่าตั้งของแผน)

11.3 ประสิทธิภาพ

  • หน้า Search ฝัง catalog 156 แห่งมาในหน้าเดียวแล้วกรองในเบราว์เซอร์ จึงตอบสนองเร็วหลังโหลดแล้ว แต่การโหลดแรกใหญ่ขึ้นเมื่อ catalog โตขึ้นหรือมีรูปมาก
  • หน้าโหลด “นักเดินป่า” รอรูปบนหน้าจอให้โหลดเสร็จ (สูงสุด 10 วินาที) บน dev server เห็นหน้า Search ครั้งแรกช้า 10–15 วินาที ซึ่งยังไม่ได้วัดบน production
  • รูปอุทยาน 123 รูปหนักราว 34 MB ใน git (ประวัติไบนารีสะสม) ควรระวังการเปลี่ยนรูปบ่อย ๆ

12. คำแนะนำและสิ่งที่ควรทำต่อ

12.1 ลำดับความสำคัญสูง (ก่อนเปิดให้คนทั่วไปใช้)

#เรื่องเหตุผล / ขั้นตอนโดยสรุป
1ย้ายการส่งอีเมลไปโดเมนของตัวเองแก้ปัญหาอีเมลเข้าสแปม/ถูกอีเมลสถาบันกรอง ใช้ผู้ให้บริการอีเมลธุรกรรม + SPF/DKIM/DMARC แล้วใส่ใน Custom SMTP ของ Supabase
2ยืนยันแผนที่หลังช่วงทดลอง Stadiaตรวจหลัง 5 พ.ย.; ตั้งแจ้งเตือนการใช้งาน; เตรียมแผนสำรองถ้าเกินโควต้าหรือเปลี่ยนเป็นเชิงพาณิชย์
3ปรับ rate limit อีเมลและเพิ่มข้อความช่วยผู้ใช้เพิ่มโควต้าต่อชั่วโมงให้เหมาะกับจำนวนผู้ใช้; แจ้งในหน้าสมัครให้ตรวจโฟลเดอร์สแปม; แจ้ง “อีเมลนี้มีบัญชีแล้ว” อย่างระมัดระวังเรื่องความเป็นส่วนตัว (ต้องตัดสินใจเชิงนโยบาย)
4ตรวจ flow ที่ล็อกอินใต้ CSP แล้วรัน production journeyเอกสารความปลอดภัยระบุว่ายังไม่ได้ตรวจการอัปโหลดรูปและแก้โปรไฟล์ภายใต้ CSP
5ตั้ง CI และเครื่องพัฒนาให้ใช้ Node 22ตัดคำเตือน Node 20 deprecated; ใส่ .nvmrc; เทสต์ในเครื่องจะผ่านครบ
6ตั้งการแจ้งเตือนค่าใช้จ่าย/การใช้งานVercel และ Supabase ตามที่เอกสารความปลอดภัยแนะนำไว้

12.2 ระยะกลาง

  • แยกฐานข้อมูล staging หรือ Supabase branch เพื่อไม่ให้ dev server เขียนข้อมูล production
  • หน้า “เครดิตรูปภาพ” รวมทั้ง 123 รูปพร้อมลิงก์ต้นทาง/สัญญา เพื่อให้ครบตามเงื่อนไข CC BY โดยไม่ทำให้การ์ดรก
  • หารูปให้ 33 อุทยานที่ยังไม่มี (ถ่ายเอง ขออนุญาตกรมอุทยานฯ หรือค้นเพิ่มจาก Commons ด้วยคำค้นอื่น) และตัดสินใจนโยบายรูปสถานที่ถาวร
  • บันทึก alt text ของรูป (เพิ่มคอลัมน์ใน photos และ RPC) เพื่อความเข้าถึงได้
  • วัดประสิทธิภาพบน production build (หน้า Search ครั้งแรก, ขนาดหน้า) แล้วพิจารณาแบ่งหน้า/โหลดรูปตามหน้าจอ
  • Nonce สำหรับ CSP เพื่อเลิกใช้ 'unsafe-inline' (ต้องเทียบกับต้นทุนที่ทุกหน้าต้อง render ตามคำขอ)
  • วางแผนสำรองข้อมูล ตรวจ/ซ้อมกู้คืนข้อมูลผู้ใช้ให้เหมาะกับแผน Supabase ที่ใช้

12.3 ฟีเจอร์ที่เลื่อนไว้ (ต้องได้รับอนุมัติก่อน)

Google login · หน้าสะสม badge · (นอกขอบเขต MVP: social, รีวิวสาธารณะ ฯลฯ) — ก่อนทำฟีเจอร์ใหม่ ให้ตรวจเป้าหมายผู้ใช้ เส้นทาง คอมโพเนนต์ data flow การแสดงผลบนมือถือ และการเข้าถึง และถามเมื่อเรื่องผลิตภัณฑ์/ดีไซน์/ข้อมูลยังไม่ชัดเจน

12.4 ข้อแนะนำการทำงานกับโค้ดนี้

  • ใช้ AGENTS.md เป็นแหล่งความจริงของพฤติกรรมที่ยอมรับแล้ว และอัปเดตพร้อมโค้ดเสมอ
  • แยก commit ตามประเภท และให้แต่ละ commit รัน tsc/lint ผ่าน (กันการแดงชั่วคราวใน CI)
  • เก็บการเขียนข้อมูลไว้ใน services/hooks ไม่ใส่ในคอมโพเนนต์แสดงผล และตรวจ loading/empty/error/focus/disabled ทุกครั้งที่แก้การโต้ตอบ
  • ห้ามเปลี่ยนแอปให้กลายเป็นตัววางแผน/จอง/โซเชียลโดยไม่ได้รับการอนุมัติ
